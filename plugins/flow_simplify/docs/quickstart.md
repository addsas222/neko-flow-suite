# 证明先行

## 先选权威模式

| | 聚焦范围 `Focused` | 全库范围 `Broad` |
| --- | --- | --- |
| **只读审计 `Survey`** | 深挖一个子系统、状态机或疑似重复点 | 分区覆盖整个仓库，给出候选、反证与盲区 |
| **授权修改 `Change`** | 证明并完成一个明确的简化边界 | 按所有权边界分批修改，每批独立验证 |

用户说"审计/调查/找候选"用 Survey；说"简化/删除/合并/重构"才用 Change。
 Survey 绝不写入目标仓库。

## 先建立契约

1. 读仓库的说明、架构与决策记录、清单文件、测试指引、生成文件约定。
2. 看版本控制状态，保留无关工作；先识别 vendored、generated、migration、
   fixture 与公共包表面。
3. 从入口点追踪运行时路径：配置、注册、分发、持久化、进程与线上边界。
4. Change 模式下找出仓库真正的验证命令，并采集一个成比例的基线。
   失败的基线会收窄最终检查能证明什么。

## 每一条候选都要形成证明记录

- 在哪个所有权边界、符号、文件，以及可验证时的行号；
- 它增加了什么维护负担；
- 生产、测试、动态和外部消费者分别是谁；
- 完整删除边界在哪里，包括共享文件内部的成员；
- 会放弃什么可观察行为或兼容性；
- 哪个最小验证可以揭示错误删除；
- 减少的复杂度是否大于新引入的迁移或替代机制。

字段不全不进入执行。找不到真实消费者、边界尚未查清，或者简化只是把复杂度
搬到别处时，保留而不是强行删除。

## 判定口径

出现以下任一情况就保留或降级：存在真实消费者；动态可达性未解决；当前决策
仍然拥有该设计；改动只是把复杂度搬走；结果超出范围或没有消除有意义的义务；
现有检查无法区分"成功"与"意外破坏"。

## 交付

Survey 交付：覆盖范围、排序后的证明记录、重要的反例与未决问题、每条不确定性
下一步所需的事实。

Change 交付：实际变更、分层验证结果、剩余风险、操作回执与可撤销路径。
一次小范围测试通过，不会被包装成完整的运行时或用户验收。

## 执行方式

`apply_cut` 只把目标移动到仓库内的 `.simplify-quarantine/`，不做行级改写。
行级改写由使用者在编辑器里完成；插件把"证明—执行—验证—撤销"框架固定下来，
并始终给出撤销路径。
